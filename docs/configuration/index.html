Make the checks fit

Describe your boundaries.

Keep architecture settings in arch-lint.config.json. Name the layers your project uses, choose which dependencies are allowed, and enable rules with settings that match the codebase.

A small starting config

{
  "extends": ["preset:recommended"],
  "scan": ["src"],
  "defaultLevel": "off",
  "layers": {
    "routes": ["src/routes/**"],
    "services": ["src/services/**"],
    "models": ["src/models/**"],
    "adapters": ["src/adapters/**"]
  },
  "allowedDependencies": {
    "routes": ["services"],
    "services": ["models", "adapters"],
    "models": ["adapters"]
  },
  "rules": {
    "architecture-graph": "error",
    "code-clone": {
      "level": "error",
      "options": { "minTokens": 50, "minLines": 6 }
    }
  }
}

An omitted dependency policy leaves that layer unrestricted. Once a layer has an entry in allowedDependencies, imports into every other configured layer are reported.

code-clone is opt-in. It reports exact repeated TypeScript and JavaScript statement runs, including a run repeated within one block. Formatting and comments do not affect a match.

Framework presets

Extend a built-in preset with preset:<name>. Each framework preset extends recommended and enables circular dependency and unused export checks with common framework entry points. 

{
  "extends": ["preset:nextjs"]
}
Preset Framework Entry points
nestjs NestJS Modules, controllers, gateways, resolvers, main.ts
nextjs Next.js App Router pages, layouts, routes, templates, pages/
express Express Routes, routers, controllers, app.* and server.*
react React App.*, app/, pages/, main.*
vue Vue JavaScript and TypeScript under views/, pages/, router/, main.*
angular Angular Modules, components, routes, routing modules, main.ts

Presets set rule options; they do not add framework parsers. Vue single-file components (.vue) are not scanned by the TypeScript and JavaScript graph engine. Put architecture-relevant exports in matching .ts or .js files.

Rule levels and scope

Set defaultLevel to off to run only the rules listed in rules. Each rule can use error or off. A rule entry can also set its layer, include patterns, exemptions, and options. 

{
  "rules": {
    "no-raw-throw": {
      "level": "error",
      "layer": "services",
      "exempt": {
        "files": ["src/services/legacy.ts"],
        "dirs": ["src/services/generated/"]
      }
    }
  }
}

Graph settings

A context groups layers into a larger boundary. Its public list marks the layers other contexts may import. Team ownership is a map from team name to the layers that team owns. abstractLayers marks layers treated as abstract in the stability-distance check. 

{
  "contexts": [
    {
      "name": "billing",
      "layers": ["billing-api", "billing-core", "billing-storage"],
      "public": ["billing-api"]
    }
  ],
  "teams": {
    "product": ["billing-api", "billing-core"],
    "platform": ["billing-storage"]
  },
  "abstractLayers": ["billing-api"],
  "adrDir": "docs/adr",
  "graph": {
    "coChange": true,
    "coChangeThreshold": 3
  }
}

graph.coChange enables co-change analysis. coChangeThreshold sets the minimum number of commits that changed a file pair together. Layer and team metrics appear in graph output when their configuration is present.

Executable architecture decisions

Markdown files under docs/adr are read by default. Set adrDir to a different directory, or to an empty string to turn this input off. Fenced archlint blocks can add layer paths and allowed or denied dependencies. 

```archlint
layer service = src/service/
layer db = src/db/
deny service -> db
```

ADR layer paths extend layers. ADR allowances extend allowedDependencies. A deny that conflicts with an allowance fails with the ADR file and line, so the decision record and config cannot disagree silently.

Adopt rules with a baseline

Existing findings can be recorded so future checks focus on new issues. Run arch-lint arch --update-baseline after enabling a rule. Review the generated baseline and commit it with the configuration. The normal run fails on findings beyond that record.

Detect worsening findings

In identity mode, matching uses a stable finding identity when a rule provides one, so message edits alone do not create a fresh finding. Findings without a stable identity use their rule, file, and message as the match key. Set baselineMode to worsening to store raw values for findings that expose numeric metrics. A new metric, a changed worsening direction, or a value moving in the configured worse direction becomes fresh. When the same metric and direction remain, unchanged or improved values remain debt. Message edits alone do not count as regressions in this mode. 

{ "baselineMode": "worsening" }

Run arch-lint arch --update-baseline after changing modes. It writes a version 5 baseline that records the selected mode and, in worsening mode, current metric values. Populated version 2 and 3 baselines remain usable in identity mode, though version 3 keeps historical message-sensitive matching for non-metric findings until refreshed. worsening mode requires refreshing populated version 2 or 3 baselines. A populated version 4 baseline, or a populated version 5 baseline created in the other mode, also requires a refresh before scanning.
